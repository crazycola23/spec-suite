# 通用约定

---

## 1. 术语表

**一个概念只允许一种写法。** 同一概念出现第二种拼写即为缺陷，不论哪种"更好看"。

| 概念 | 代码标识 | 数据库 | 中文（仅 UI） | 禁止写法 |
|---|---|---|---|---|
| <项目> | `project` | `<前缀>_project` | 项目 | ~~item~~ / ~~task~~ |
| <发布记录> | `publishRecord` | `<前缀>_publish_record` | 发布记录 | ~~post~~ / ~~article~~ |

命名规则：

| 位置 | 风格 | 例 |
|---|---|---|
| Java 类 / TS 类型 | PascalCase | `PublishRecord` |
| Java 字段 / TS 字段 / JSON 键 | camelCase | `publishRecord` |
| 数据库表 / 列 | snake_case + 统一前缀 | `<前缀>_publish_record.retry_of` |
| 枚举值 | <SCREAMING_SNAKE 或 lower_snake，二选一，全库统一> | `PROJECT_CREATED` |
| 权限码 | `<域>:<对象>:<动作>` | `<前缀>:budget:release` |
| 错误码 | `<正则>` | `<GEO-40901>` |

**禁止一个概念三种拼写。** 出现 `publishRecord` / `publish_record` / `postRecord` 混用时，前端和后端会各自建一套映射，然后其中一套忘记更新。

## 2. 错误信封

所有非 2xx 响应统一信封：

```json
{
  "bizCode": "<GEO-40901>",
  "message": "<面向用户的文案，前端可直接展示>",
  "details": { "existingId": "..." },
  "requestId": "<用于查日志，必须返回>"
}
```

### 2.1 `bizCode` 是前端唯一的分支依据

**前端不许按 HTTP status 分支，不许按 message 文本分支。** 只按 `bizCode`。

由此推出一条硬约束：**一个码只能有一个语义。** 同一个码既表示"重放成功"又表示"业务冲突"，前端必然误渲染 —— 这类缺陷在真实项目里出现过，成因就是复用了一个已有码而不是新增一个。

`details` 里放**字段名**，不放中文说明。前端要跳转到冲突对象时用 `details.existingId`，而不是解析 message。

### 2.2 `warnings[]`

2xx 响应可携带 `warnings[]`，元素结构与错误信封相同。**前端必须渲染它** —— 不渲染就等于服务端的提示不存在。

`warnings[]` 用于"操作成功了但有事需要知道"。不要用它表达失败。

---

## 3. 分页与排序

```json
{ "items": [], "total": 0, "page": 1, "size": 20 }
```

**每个列表接口必须有确定的全序。** 业务排序键有重复值时，追加一个唯一列兜底（通常是主键或创建时间 + 主键）。

否则分页会漏行或重复行 —— 数据库对相等键的返回顺序不保证稳定，这个 bug 只在生产数据量下出现。

## 4. 并发

### 4.1 乐观锁

可编辑实体带 `version` 列。更新语句 `WHERE id = ? AND version = ?`，影响行数 0 即冲突。

### 4.2 冲突响应必须给出差异

冲突时返回：

```json
{
  "bizCode": "<冲突码>",
  "details": {
    "currentVersion": 7,
    "submittedVersion": 5,
    "changedFields": ["ownerId", "budgetCap"]
  }
}
```

`changedFields` **框架不会给，必须自己算**。省掉它，前端只能提示"请刷新重试"，用户重试时会再次覆盖别人的修改。

### 4.3 禁止静默覆盖

不允许"最后写入者胜"。也不允许把冲突降级成 warning 后继续写。

---

## 5. 幂等

### 5.1 传输层与业务层是两件事

| | 传输层重放 | 业务幂等冲突 |
|---|---|---|
| 触发 | 客户端重发同一个 `<幂等键请求头>` | 业务上该对象已存在 |
| 响应 | 首次的响应体 + 响应头标记重放 | 4xx + 冲突码 + `details.existingId` |
| 谁负责 | 拦截器 + 缓存首次响应 | 数据库唯一键 |

**不要用同一个码表达这两件事**（见 §2.1）。

只缓存 2xx 首次响应；4xx/5xx 不进重放缓存，否则一次瞬时故障会被固化。

### 5.2 业务幂等靠数据库，不靠应用层判断

"先查再插"在并发下必然失败。用唯一键。

### 5.3 条件唯一：生成列技巧

需要"同一对象同时只能有一个活跃记录，但历史记录不限"时，不要在应用层判断。加一个生成列：

```sql
active_key VARCHAR(64) GENERATED ALWAYS AS (
  CASE WHEN status IN (<活跃态列表>) THEN CONCAT(<对象id>, ':', <维度>) ELSE NULL END
) STORED,
UNIQUE KEY uk_active (active_key)
```

NULL 不参与唯一约束，所以历史记录不限量，活跃记录被数据库强制唯一。

**`active_key` 的列元组必须与业务规则点明的维度完全一致。** 这里最容易出现三方不一致：规则说两列、契约文档写三列、DDL 实现两列。裁决依据是业务规则，契约文档是缺陷。

## 6. 第三方调用四步铁律

> 这一节是全套里最容易被省略、被省略后代价最大的一节。
> **不要对第三方结果做乐观假设。** 这是资损的最常见成因。

任何有外部副作用的调用，必须四步：

```
1  落库：先写一条请求记录（状态 = 发起中），带幂等键。此时还没调
2  调用：拿到结果
3  回写：把结果写进那条记录（成功 / 失败 / 未知）
4  对账：定时任务捞出所有停在"发起中""未知"的记录，去查
```

省掉第 1 步，进程在第 2 步崩掉时就没有任何痕迹 —— 动作可能已经生效，而系统不知道。
省掉第 4 步，"未知"态就是永久泄漏。

### 6.1 结果 → 允许的下一步动作

超时**不是失败**。它是第三种结果，必须单独建模。

| 第三方返回 | 动作是否可能已生效 | 允许的下一步 | 禁止 |
|---|---|---|---|
| 明确成功 | 是 | 继续业务流程 | — |
| 明确失败（且确认无副作用） | 否 | 重试 | — |
| 明确失败（副作用不确定） | 未知 | 查询接口确认 | **重试** |
| 超时 / 连接中断 | 未知 | 查询接口确认 | **重试** |
| 返回了未识别的状态 | 未知 | 查询接口确认 + 人工 | **重试**、**当成失败** |

**"未知"永远不允许直接重试。** 只允许查。没有查询接口 → "未知"就是终态，只能人工处理，且要在规格里写明这一点，不要留一个看不见的重试按钮。

### 6.2 重试次数由数据库强制

允许重试一次，就加 `UNIQUE KEY uk_retry_once (retry_of)`。不要靠应用层计数 —— 计数会因并发或重启失效。

## 7. 金额、时间、ID

| | 约定 | 理由 |
|---|---|---|
| 金额 | 整数最小单位（分）+ 独立币种列 | 浮点不可用于金额；无币种的金额是无意义的 |
| 金额展示 | 只在 UI 层除以 100 | 服务端一律传整数 |
| 时间存储 | UTC | — |
| 时间传输 | ISO-8601 带偏移 | 不传"2026-08-19 10:00"这种无时区串 |
| 业务日期边界 | 明确写清用哪个时区判"今天" | 跨时区团队必踩 |
| 主键 | <雪花 / UUID / 自增，全库统一> | — |
| 对外 ID | 不暴露自增主键 | 可枚举 |

## 8. 审计与不可变

审计/台账类对象**只许 INSERT**。不许 UPDATE、不许 DELETE、不许逻辑删除。

由此推出：这些表**不带** `version` / `update_by` / `update_time` / `del_flag` 列。带了就说明有人打算改它。

- 成功动作的审计与业务写入**同事务**。事务回滚，审计也该回滚
- 授权拒绝的审计**独立事务追加**（业务事务已经回滚了，但拒绝事实必须留下）
- 审计内容不含密钥、令牌、不可导出的敏感字段
- 导出审计这个动作本身也要写审计

**强制层要写清楚。** 只在 ORM/Mapper 层拦截 UPDATE，就在 `CLAUDE.md §6` 如实标"⚠️ 部分：数据库无 trigger/grant"。写 ✅ 会让下一个人以为绕过 ORM 也安全。

## 9. 前端五态

每个数据视图必须实现五态，缺一态不算完成：

`加载中` · `空` · `错误（带 requestId）` · `无权限` · `正常`

**"无权限"与"空"必须视觉可区分。** 二者混同时，用户会以为数据不存在，然后去问为什么数据丢了。

**按钮的可用性来自服务端。** 服务端返回 `allowedActions[]`，前端照着渲染。前端不许按状态自行推断哪些按钮可用 —— 那等于把状态机实现了第二遍，两份实现一定会分叉。
